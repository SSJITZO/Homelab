# Incident Report: Suricata Sensor Showing Zero Detections Post-Relocation

**Date:** 2026-09-27
**Affected system:** Pi 2 — IDS Sensor (Suricata, Lab VLAN — 192.168.50.20)
**Severity:** Low (no security impact — detection capability degraded, not compromised)
**Status:** Resolved

## Summary

Following a physical relocation of the home lab, the intrusion detection sensor (Suricata, running on a Raspberry Pi 5) appeared to be non-functional: test traffic designed to trigger known-signature alerts produced no log entries. Root cause was a DNS misconfiguration unrelated to Suricata itself — the sensor was configured to use its own IP address as its DNS resolver, causing all outbound DNS lookups to fail silently. Suricata was healthy and actively logging throughout; the appearance of failure was caused entirely by the test traffic never being able to reach its destination.

## Timeline

| Time | Action | Result |
|---|---|---|
| T+0 | Ran `curl http://testmynids.org/uid/index.html` to generate test alert traffic | `curl: (6) Could not resolve host` |
| T+2 | Checked `sudo grep "GPL ATTACK_RESPONSE" /var/log/suricata/fast.log` | No matching entries |
| T+5 | Inspected `/etc/resolv.conf` | Found `nameserver 192.168.50.20` — the host's **own** IP |
| T+8 | Edited `/etc/resolv.conf`, set `nameserver 1.1.1.1` | — |
| T+9 | Re-ran test | Still failed — DNS server itself unreachable at that moment |
| T+11 | `ping -c 4 1.1.1.1` | 0% packet loss, ~20ms latency — confirmed general internet connectivity was healthy |
| T+13 | `nslookup testmynids.org 1.1.1.1` | `NXDOMAIN` — a valid response, but the domain no longer exists |
| T+14 | `nslookup google.com 1.1.1.1` | Resolved correctly with multiple A/AAAA records — **confirmed DNS fully functional** |
| T+16 | Switched to a known-active IDS test domain: `curl -A "BlackSun" http://testmyids.com` | Request succeeded, returned `uid=0(root) gid=0(root) groups=0(root)` |
| T+17 | `sudo grep -c '"event_type":"alert"' /var/log/suricata/eve.json` | Returned `2` — confirmed detection |

## Root cause

`/etc/resolv.conf` had been auto-generated by NetworkManager with the sensor's own address (`192.168.50.20`) listed as a DNS nameserver — likely inherited from a VLAN DHCP configuration during the network rebuild after relocation. Because the Pi runs no DNS service, every outbound DNS query silently timed out with no error surfaced to the user beyond curl's generic resolution failure.

A secondary contributing factor: the original test domain (`testmynids.org`) used to validate the sensor no longer resolves to an active host (`NXDOMAIN`), independent of the DNS misconfiguration — this masked the fix's success on the first retry and required switching to a currently-active test target (`testmyids.com`).

## Resolution

1. Manually corrected `/etc/resolv.conf` to include a working public resolver (`1.1.1.1`)
2. Verified resolution with a known-good domain before re-testing detection
3. Switched to a currently-active IDS test service after confirming the original test domain was defunct
4. Confirmed detection with two-sided alert evidence (outbound request flagged + inbound response flagged)

## MITRE ATT&CK mapping

- **T1071 — Application Layer Protocol:** the outbound request used a known malware-associated HTTP user-agent string, consistent with a C2 (command-and-control) beacon over standard web traffic.
- **T1059 — Command and Scripting Interpreter:** the returned response (`uid=0(root)...`) mimics the output pattern of a remotely-executed shell command, consistent with post-exploitation command execution.

## Lessons learned / follow-up actions

- **Diagnostic order matters.** Confirming basic connectivity (`ping`) before assuming a higher-layer service (DNS, then the application) is broken avoided misdiagnosing this as a Suricata failure.
- **Validate test infrastructure independently of the system under test.** The dead test domain (`testmynids.org`) could have caused a false "still broken" conclusion even after the actual fix was applied.
- **Action item:** add a DNS health check to the planned Wazuh SIEM deployment so a misconfigured resolver on any sensor is surfaced automatically rather than discovered manually during the next test.
- **Action item:** pin DNS at the NetworkManager connection-profile level (`nmcli connection modify ... ipv4.dns`) rather than editing `/etc/resolv.conf` directly, since the latter can be silently overwritten on reconnect.
